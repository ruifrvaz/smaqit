# `smaqit.feature-deploy` — Standalone Post-MVP Deployment Skill

**Status:** Completed
**Created:** 2026-07-23
**Completed:** 2026-07-23

## Description

When a post-MVP feature is ready to deploy, there is no clear entry point. `smaqit.new-greenfield-project` is a full 8-phase lifecycle for brand-new projects — you can't skip to Phase 4/5. `smaqit.feature-new` runs a full 5-phase feature cycle, not just deployment. `/smaqit.deployment` can be invoked standalone, but follows `framework/PHASES.md`'s abstract Deploy phase definition — it lacks the operational knowledge encoded in greenfield's Phase 4/5 (which infrastructure skills to invoke, in what order, how to branch on `provisioning_mode`, how to match a deploy skill by stack type).

`smaqit.feature-deploy` fills this gap. It extracts greenfield's Phase 4/5 deployment logic into a standalone, post-MVP deployment skill. It is "feature-aware" — a pre-phase reads specs to identify what's being deployed (stack, target, provisioning mode) — and hands a well-formed deployment context to `/smaqit.deployment`, which remains domain-agnostic. The deployment agent receives an explicit plan rather than deriving one from abstract phase descriptions.

Post-MVP deploys go through the existing CI/CD pipeline (GitHub Actions workflows generated during the original greenfield run). No dev-VM sweep, no deploy-rsync skills — this is the Nth deploy on infrastructure already proven.

## Design Decisions

- **New skill, not a mode on greenfield or feature-new.** Greenfield is a full lifecycle; feature-new is a full feature cycle. Feature-deploy is a single-purpose deployment skill that both can delegate to. This avoids duplicating the provisioning_mode branching across two skills and gives users a clear `/smaqit.feature-deploy` entry point.
- **Pre-phase identifies what's being deployed.** Reads `specs/stack/platform-stack.md` and `specs/infrastructure/*.md` to determine the stack, target, and provisioning_mode before any infrastructure work begins. This is the "feature awareness" that the deployment agent currently lacks.
- **Provisioning mode defaults to `existing-owned`** when an Infrastructure spec shows `status: deployed` — same override as `smaqit.feature-new`, since post-MVP projects already have a deployed target. Only elicits if ambiguous.
- **Infrastructure readiness is extracted from greenfield Phase 4.** The vault-loader → provision-cyso (skip if existing-shared) → vm-bootstrap sequence, with all three provisioning_mode branches, lives in this skill. The deployment agent doesn't need to know about this.
- **Deployment goes through CI/CD, not deploy-rsync skills.** Post-MVP, the CI/CD pipeline already exists (generated by `cicd-generate` during greenfield). Feature-deploy pushes to main, monitors the workflow, and verifies — no manual rsync, no deploy-skill matching. This is the Nth deploy on a proven pipeline.
- **`/smaqit.deployment` agent is NOT modified.** It remains domain-agnostic. Feature-deploy invokes it for its existing responsibilities (spec validation, frontmatter updates, deployment report). The CI/CD push/monitor/verify sequence is feature-deploy's own prose, not the agent's.
- **Amendment gate runs post-deploy** (reuses `check-amendments.sh` by reference, same as greenfield Phase 8 and feature-new Phase 3).

## Implementation Steps

1. **Author `skills/smaqit.feature-deploy/SKILL.md`** following `templates/skills/base-skill.template.md` and `framework/SKILLS.md` conventions. Model the overall shape on `smaqit.new-greenfield-project` and `smaqit.feature-new`. Phase structure:

   **Pre-phase — Feature Identification:**
   - Read `specs/stack/platform-stack.md` — determine the declared stack (authoritative source, do not re-derive from filesystem)
   - Read `specs/infrastructure/*.md` — determine deployment topology, target, current status
   - Resolve `provisioning_mode`: if infra spec shows `status: deployed`, default to `existing-owned` (override `smaqit.input-deployment`'s generic `provision` default). Only elicit if genuinely ambiguous. If resolution falls through to `provision` despite infra spec existing, stop and flag.
   - Confirm CI/CD workflows exist (`.github/workflows/deploy.yml` at minimum) — they were generated during greenfield. If absent, stop and flag that the project hasn't completed its initial greenfield run.
   - Gate: stack identified, provisioning_mode resolved, CI/CD confirmed present.

   **Phase 1 — Infrastructure Readiness:**
   - Extracted from greenfield Phase 4 steps 2–5, with all three provisioning_mode branches:
     1. Invoke `smaqit.infrastructure-vault-loader` — mode-aware (skip cyso/tfstate if existing-shared; run bootstrap-app-to-machine.sh if existing-shared)
     2. Invoke `smaqit.infrastructure-provision-cyso` — skip entirely if existing-shared; expected no-op if existing-owned (gated by plan-guard.sh)
     3. Invoke `smaqit.infrastructure-vm-bootstrap` — use Terraform fixed_ip or manual VM_HOST
   - Gate: all infrastructure preconditions confirmed.

   **Phase 2 — Deploy via CI/CD:**
   - Invoke `/smaqit.deployment` agent for spec validation, frontmatter updates, and deployment report
   - Invoke `smaqit.infrastructure-repo-config` — restricted mode if existing-shared (skip tfstate/cyso, sync only ssh + github)
   - Push to main: `git push origin main` — triggers the existing `deploy.yml` workflow
   - Monitor pipeline: `gh run watch`
   - Invoke `smaqit.infrastructure-deploy-verify` against production
   - Run amendment gate: `bash [SMAQIT_SKILLS_DIR]/smaqit.new-greenfield-project/scripts/check-amendments.sh specs/`
   - Gate: CI/CD succeeds, deploy-verify PASS, amendment gate clear.

   **Phase 3 — Close-out:**
   - Confirm deployment report written
   - Re-run amendment scan (belt-and-suspenders)
   - If this is a standalone deploy (not part of a feature-new cycle): invoke release workflow (`smaqit.release-analysis` → `smaqit.release-approval` → …). If invoked from within feature-new, skip — feature-new owns release tagging.

2. **Do NOT modify `agents/deployment.md`.** The deployment agent is invoked as-is. The CI/CD push/monitor/verify sequence is feature-deploy's own prose steps, not delegated to the agent.

3. **Reference `check-amendments.sh` via `[SMAQIT_SKILLS_DIR]` placeholder** — same cross-skill reference convention as greenfield Phase 8 and feature-new Phase 3.

4. **Add a one-line mention to `README.md`** alongside `smaqit.feature-new`.

## Notes

- This skill is intentionally CI/CD-only for the deploy step. If a project's greenfield run didn't complete (no CI/CD workflows exist), feature-deploy stops and flags it — the correct path is to finish greenfield first, not to fall back to manual rsync.
- The deployment agent (`agents/deployment.md`) is NOT in the Files to Modify list — zero changes. Feature-deploy invokes it for what it already does; the CI/CD orchestration is feature-deploy's own prose.
- Release tagging is conditional: if this deploy is part of a feature-new cycle, feature-new owns the release. If standalone, feature-deploy runs the release workflow.
- `smaqit.feature-new` may eventually delegate its Phase 3 (Deployment) to this skill — flagged as a natural follow-up, not in scope for initial implementation.
