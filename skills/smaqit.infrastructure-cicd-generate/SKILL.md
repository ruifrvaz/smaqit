# CI/CD Workflow Generator

## Generation Mode

- **`full`** (default) — this project provisions and manages its own VM's Terraform state.
  Generates all 3 workflows with a `provision` job.
- **`deploy-only`** — `provisioning_mode: existing-shared` (see `smaqit.new-greenfield-project`
  Phase 4/5): this project deploys onto a VM a *different* project owns and provisions. No
  Terraform step is generated at all, and `provision.yml` is not generated.

## Steps

1. **Read existing workflows** from `.github/workflows/`. If workflows exist and are substantially complete, offer to diff rather than overwrite.

2. **Resolve configuration values** from Infrastructure specs and `CLAUDE.md` (or `copilot-instructions.md`). Use these defaults if not found:

   | Reference | Default (`full`) | Default (`deploy-only`) |
   |-----------|-------------------|--------------------------|
   | VM host | `${{ vars.VM_HOST }}` — a repository variable, not a secret (just an IP/hostname; see `smaqit.infrastructure-repo-config`) | `${{ vars.VM_HOST }}` — same variable, set manually since there's no Terraform run on this project's side to derive it from |
   | SSH key secret | `VM_SSH_KEY` | `VM_SSH_KEY` |
   | Terraform backend | `TF_BACKEND_ACCESS_KEY`, `TF_BACKEND_SECRET_KEY` | not used |
   | Cloud credentials | `TF_VAR_APP_CREDENTIAL_ID`, `TF_VAR_APP_CREDENTIAL_SECRET` | not used |
   | GitHub token (Terraform) | `GH_TERRAFORM_TOKEN` | not used |
   | Terraform path filter | `deployment/terraform/**` | not applicable — no Terraform |

3. **Generate `deploy.yml`:**
   - **`full`:** two sequential jobs:
     - `provision` job: runs `smaqit.infrastructure-provision-cyso/scripts/plan-guard.sh` and fails the
       job before ever reaching `terraform apply` if the plan shows a `delete`/`replace` action. Never
       generate a bare `terraform apply -auto-approve` with no gating step in front of it. Env MUST
       include `TF_VAR_github_token: ${{ secrets.GH_TERRAFORM_TOKEN }}` — NOT `GITHUB_TOKEN` (reserved;
       runner overwrites it before steps execute).
     - `deploy` job: `needs: [provision]`. Steps in order: checkout → setup Node.js → install deps → build backend → build frontend (with `VITE_DEMO_MODE: ${{ vars.VITE_DEMO_MODE }}` on the build step) → rsync backend dist → rsync frontend dist → install node_modules on VM via Docker → write deploy stamps → docker compose restart → `systemctl reload-or-restart nginx` (not a bare `reload` — see Gotchas).
   - **`deploy-only`:** a single `deploy` job, no `provision` job, no `needs:`, no Terraform step
     of any kind. Same step sequence as the `full` mode's `deploy` job (checkout → setup Node.js →
     install deps → build backend → build frontend → rsync → Docker → deploy stamps → docker
     compose restart → `systemctl reload-or-restart nginx`), reading the VM host from the same
     `${{ vars.VM_HOST }}` variable as `full` mode.

4. **Generate `provision.yml`:**
   - **`full`:**
     - Trigger: `pull_request`, paths filter `deployment/terraform/**`
     - Single `plan` job: runs `plan-guard.sh` and surfaces its PASS/BLOCKED verdict in the posted PR
       comment, alongside the raw `terraform plan` output — NO `terraform apply`
     - Same env vars as the `provision` job in `deploy.yml`, including `TF_VAR_github_token`
   - **`deploy-only`:** do NOT generate this file. There is no Terraform to plan.

5. **Generate `post-merge-deploy.yml`** with:
   - Trigger: `pull_request`, `types: [closed]`
   - Condition: `if: github.event.pull_request.merged == true && contains(github.event.pull_request.body, 'smaqit:deploy')`
   - Action: trigger `deploy.yml` via `workflow_dispatch`
   - Do NOT use a label trigger — Copilot Coding Agent tokens lack `issues:write` and cannot apply labels.
   - Generated identically in both modes.

6. **Write files to `.github/workflows/`** — 3 files (`full`) or 2 files (`deploy-only`: `deploy.yml` + `post-merge-deploy.yml`, no `provision.yml`).

7. **Report** the list of files written with a brief description of each, including which generation mode was used.

## Output

- **`full`:** `.github/workflows/deploy.yml` (provision + deploy sequential jobs), `provision.yml` (PR-only terraform plan with PR comment), `post-merge-deploy.yml` (body sentinel trigger for deploy.yml)
- **`deploy-only`:** `.github/workflows/deploy.yml` (single deploy job, no Terraform), `post-merge-deploy.yml` (body sentinel trigger for deploy.yml) — no `provision.yml`

## Scope

- Does NOT set up GitHub Secrets or Variables — use `smaqit.infrastructure-repo-config` for that.
- Does NOT provision infrastructure — Terraform runs inside the generated workflow (`full` mode only; `deploy-only` mode has no Terraform at all).
- Does NOT handle matrix builds, monorepos, or container registry pushes.

## Examples

**Input:** New project with no CI/CD workflows. Operator invokes `/cicd.generate`.
**Output:** 4 files written to `.github/workflows/`. `deploy.yml` has sequential provision→deploy jobs; `provision.yml` is PR-only plan with PR comment; `post-merge-deploy.yml` uses body sentinel; `copilot-setup-steps.yml` has checkout.

## Gotchas

- **`GITHUB_TOKEN` is reserved** — GitHub Actions runner injects its own short-lived installation token under `GITHUB_TOKEN` before any step executes, overwriting any `env.GITHUB_TOKEN` set by the workflow. Use `TF_VAR_github_token`; Terraform auto-maps `TF_VAR_*` → `var.*`.
- **PR body sentinel, not label** — Copilot Coding Agent tokens lack `issues:write`. `post-merge-deploy.yml` MUST use `contains(github.event.pull_request.body, 'smaqit:deploy')`, not a label check.
- **`provision.yml` also needs `TF_VAR_github_token`** — omitting it causes interactive prompt hangs in PR preview plans.
- **`copilot-setup-steps.yml` must include `actions/checkout@v4`** — without checkout, the Coding Agent cannot read the codebase of a private repository.
- **`VITE_*` vars are build-time** — pass `VITE_DEMO_MODE` and any other `VITE_*` vars to the `npm run build` step, not the deploy step. Vite bakes them at compile time; they are not available at runtime.
- **`.terraform.lock.hcl` must be committed** — do NOT add it to `.gitignore`. If CI fails with provider version errors, check that this file is tracked in git.
- **Never generate a bare `terraform apply -auto-approve`** — always gate it behind
  `smaqit.infrastructure-provision-cyso/scripts/plan-guard.sh`. A `user_data` edit (even a
  comment-only one) forces VM replacement, and an ungated `apply` in CI will carry it out
  unattended. This is a deterministic script check, not a prose instruction to "review the plan."
- **`systemctl reload nginx` fails if nginx was never started** — cloud-init's `enable` only arranges
  start-on-next-boot. Generate `reload-or-restart`, not `reload`, in the deploy job.

## Completion

- [ ] Existing workflows read (or confirmed absent)
- [ ] Generation mode determined (`full` or `deploy-only`)
- [ ] Configuration values resolved (mode-appropriate defaults table)
- [ ] `deploy.yml` written — `full`: provision + deploy jobs, sequential, `plan-guard.sh` gates the apply, no GITHUB_TOKEN collision. `deploy-only`: single deploy job, no provision job, no Terraform step
- [ ] `provision.yml` written (`full` only — PR-only, plan only via `plan-guard.sh`, path filter, `TF_VAR_github_token` present); NOT generated in `deploy-only` mode
- [ ] `post-merge-deploy.yml` written (body sentinel, no label dependency) — both modes
- [ ] Report delivered, stating which generation mode was used

## Failure Handling

| Situation | Action |
|-----------|--------|
| Required input not provided | Request the missing information before proceeding |
| Gathered input is ambiguous | Flag the ambiguity and ask for clarification |
| Subagent invocation fails | Report the failure with context; do not silently retry |
| Output artifact already exists | Confirm with user before overwriting |
| Workflows already exist and differ | Show a diff summary; ask whether to overwrite or merge |
| Infrastructure spec not available | Use defaults for all VM and Terraform references; note which values need to be updated post-generation |
| Configuration value ambiguous | Apply the documented default; annotate the generated file with a `# TODO: verify` comment |
| Generated `deploy.yml` has no plan-guard gate in front of `apply` | Add the `plan-guard.sh` invocation step before `terraform apply`; this is not optional — applies to `full` mode only, since `deploy-only` mode has no `apply` step to gate |
| `deploy-only` mode requested but a `provision.yml` already exists from a prior `full` generation | Ask whether to delete the stale `provision.yml` — leaving it in place would plan Terraform that no longer matches this project's `provisioning_mode` |
